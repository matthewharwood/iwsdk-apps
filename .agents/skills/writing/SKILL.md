# Project writing

Lead with what the reader can do, then the commands or facts they need. Keep commands, paths, names and versions accurate to the repository. Prefer an executable quick start over a stack advertisement.

Distinguish a reusable template, its example app, and product-specific work. The token-game demonstrator proves infrastructure; do not describe it as a complete MTG rules engine. A heuristic is not a trained model, a fixture is not model-quality evidence, and a desktop check is not physical-headset validation.

Describe durable, temporary, unavailable and locked storage in terms of what happens to the user's save. Explain recovery actions plainly. Keep implementation details out of ordinary game controls unless users need them to make a decision.

Document what was actually run and observed. Do not copy test counts or production claims from Snapmatch. Say when device, deployment or offline behavior is unverified. A compile/build pass alone does not justify “fully functional.”

Keep one canonical instruction source and link to it. Update generator commands and skill references when files move. Do not add repeated routing manuals, stale approval policies or provider publishing assumptions to prose.
